# US100 副本包布局恢复（静态法，2026-09-18）

**2026-11-23 校正，适用于 2.24.0.124。** 本页下方是九月排查时的记录。原生枚举中 CMD217 是 `OVERFLOW_INFO`，客户端用 CMD37 确认房间加载。CMD16 的成功回复为单字节 `01`。单人同频道 NOTI9 长 72 字节，成员数在偏移 47，槽位在 48，角色编号在 49。普通单人 NOTI28 长 41 字节，种子在偏移 19。NOTI29 的怪物数在偏移 18，每个怪物占 25 字节，Mirkwood 首房含四个怪物，共 123 字节。NOTI30 是五字节的加载结束通知。

> **结论（2026-09-20 实测）：副本门口应答必须是最小集 —— 只发"ACK(15) + ENTER_SELECT(27)"。**
>
> 2026-09-18 06:24 那次会话（`runtime/cursor/events.jsonl`）是唯一保留下来、客户端**确实开过选择
> 界面**的记录：它的场景上报是 `0x09`（选完副本），而且日志里能看到客户端自己发出
> `SELECT_DUNGEON(16)`。那一次服务端在门口只回了两个包：
>
> ```
> 服务端 → 15 ACK (body 01)
> 服务端 → 27 (ENTER_SELECT, 36 字节全零)      ← 没有 0003/001A/0005/0164/0017/0009
> ```
>
> 后来按参考资料加进去的那些"同伴包"（`0003` USER_STATE、`001A`、`0005` 权限表、`0164`、
> `0017` area=0xFF、`0009`）**会把选择界面挡掉**：加上它们时客户端只在 11 ms 内上报 `0x64`
> 并把角色送进过渡态，界面永不出现。同一批会话里另一个真实缺陷是 `0003` 的状态字节被写成
> `1`，而这个客户端 `1` 的含义是"角色在副本里"（`internal/game/protocol/user_state.go`：
> 城镇 0 / 副本 1），于是角色在城镇门口直接消失。
>
> 2026-09-20 用最小集实测通过：客户端发出 `SELECT(16)`（副本 3），服务端回 `28/29` 后客户端
> 上报 `0x09`，加载阶段（`37/3/30`）随之完成 —— 这条链路第一次走通到房间加载。
>
> 各个同伴包现在都是 `configs/us100/gate-set.json` 里的开关（`minimal_gate`、`gate_ack`、
> `enter_select`、`user_area_select`、`party_preload`、`candidate_list`、`reference_order`、
> `enter_select_state`），可以一次开一个来定位是哪一个挡掉了界面。

u32@39, u8@43` —— 于是客户端从此处开始读到我们的 `0xff` 填充，副本加载再也不会启动。

## 选择确认为什么"什么都不发生"

客户端处理 id=16 的代码里，每一条失败路径都是**静默返回**（没有日志），所以界面不会报错、
也不会前进。它的第一步是 `0x143b1e100(条目里的 u16)` —— 反汇编后确认那是一个**泛型容器
索引**（`container[edx]`，带 `0 <= edx < [container+0x60]` 的边界检查，越界返回 0）：
条目里的"地牢ID"其实是**客户端容器里的下标**，容器为空或越界就整条跳过。

该容器由全局 `0x149788ec8` 指向的对象持有（同一全局也被 id=15/16 选择链路与大量 UI 代码
引用），其内容来自服务端下发的候选列表 —— 而我们的 `id=27` 发的是 **36 字节全零**（空列表）。
这与"地图界面能打开（用客户端自带数据）、但按下进入没反应（服务端列表为空 → 下标查不到）"
的现象完全吻合。

id=27 的真实结构（读序列 + 分支）：

```
u8@0 计数A, u8@1 计数B,
u32@2, u32@6, u8@10,
[计数A × u16]（循环，读入本地数组后交给 UI/状态调用）,
u32@13, u8@17, [计数B × u16]（循环）,
u8@20, [u16 循环]@21, u8@23
```

## 参考源码（90USDOF）带来的结论与当前状态（2026-09-18）

用户提供了权威参考：`E:\BaiduNetdiskDownload\DNF服务器源码\90USDOF源码20260810-server-source-portable`
（含 `PacketEnum_current_USDOF_Stage3.h` 命令号枚举与 `server_proto/game/dungeon/` 完整实现）。据此确认：

- `15/16` 是**客户端→服务端**（`ENTER_SELECT_DUNGEON`/`SELECT_DUNGEON`），`27/28/29` 才是服务端→客户端。
- 客户端 `SELECT_DUNGEON` 请求体 = **17 字节**：`u32 地牢ID | u8 难度 | u16 进入选项 | u8 mode2 |
  u8 sso | u16 extra16 | u32 extra32 | u8 tail0 | u8 tail1`。
- **`27` 的 US 载荷 = 27 字节**（`u32 mode=1 | u32 reserved | u8 数量 | u8 | u8 | u32 | u16 | u16 |
  u32 | u8 | u8(n4) | u16`）。此前发 36 字节全零、`mode=0`，是"选择界面不推进"的直接原因，改对后
  客户端**进入了副本过渡态**（人物传送到入口并消失，状态上报从 `0x1b` 变 `0x64`）。
- **wire 里没有 HP 字段**："客户端按 maze 读 PVF" —— `-nan(ind)%` 是客户端不在副本/房间上下文
  时的显示，不是缺包。属性通道方向据此关闭。
- 参考的"进入选择"包集合为 `0164 → 02FD → 02FE → 02E6 → 0005 → 0017 → 0002 → 0003 → 001A →
  050E → 001B → 0009`，但**不能照抄顺序**：实测照该顺序（并加 02E6/0017/0009）后客户端连传送都
  不做，已回退到能进过渡态的顺序：`3 → 26 → 766 → 765 → 356 → 5 → 27`。

**当前状态**：副本入口已通（客户端进入过渡态），房间数据（28/29）是唯一缺口。因为客户端在该
状态下不再发 `SELECT_DUNGEON(16)`，网关现在在收到 `217` 且状态字节为 `0x64` 时**直接按角色
允许的副本启动会话**（`startAllowedDungeon`，合成 17 字节请求体）并下发 `DUNGEON_INFO` 与
`START_MAP`。下一步验证是否出现房间场景；若仍停在过渡态，按参考补 `0002`/`050E` 与
`START_MAP` 之后的 `0117`/`019F`，每次只加一个变量。

## 2026-09-18 20:35 会话存档给出的实证（关键）

上一轮的 `events.jsonl` 被启动脚本的 `rmtree` 删掉，导致每次失败都无据可查；现在启动脚本把

→ 服务端依次发 3, 26, 766, 765, 356, 5, 27, 27   ← 27 连发两次
11 ms 后客户端上报 id=217，体 = 0064010000000000（状态字节 0x64）
→ 服务端自动启动被拒: "dungeon 7110 is not this character's source starting route"

补充事实：`us100a`(id=39) 的起始路线阶段是 **3=已完成**（`character_birth` 表，见 `tools/dbbirth.py`），

## 本客户端 `id=27` 的真实读序列（推翻 mode=1 的照抄）

`tools/extract_reads_sized.py 0x351e670 0x260`（handler `0x14351e670`）：

```
u8@0, u8@1, u32@2, u32@6, u8@10（循环次数）, [u16]×次数, u32, ...
```

`0x351e674..0x2c0` 的代码确认：前两个字段是**两个独立 u8**，第 5 个字段（偏移 10）是**循环次数**，
循环体读取 `u16` 到一个 16 字节的局部数组（预置 0xffff，只能放 8 个 u16）。**偏移 0 不是 u32 mode**。

参考资料的 `u32 mode = 1` 体在本客户端上会让 u8@0 = 1，走**另一个分支**（`0x144e39a70` +
`0x144e4c080(obj, 2)`），实测后果就是 20:35 的存档：客户端**不打开选择界面**，直接把角色送进
过渡态（状态字节 0x64），并且此后不再发 `SELECT_DUNGEON`。而**全零 36 字节**体（本客户端
`protocol.EnterDungeonSelection()`）是此前"选择界面能开（状态 0x1b）、按进入没反应"的形态。

因此 gate 已改回发全零 36 字节体；`EnterDungeonSelectionUS()` 保留但标注**仅作参考、本客户端不适用**。

## 仍然开放的问题

选择界面打开后，按"进入"没有反应：客户端 `id=16` 的处理器把条目里的 u16 当**容器下标**
（容器全局 `0x149788ce8`）。该容器的内容来自服务端下发的列表，而 20:35 与 20:47 两次会话里
客户端**都没有发出 `id=16`**（前一次是界面没开，后一次是根本没进界面）。下一步取证：
让界面打开后按下进入，抓 `id=16` 的**真实请求体**（`events.jsonl` 已按 `observedGameRequest`
保留 16 的正文），据此判断客户端发的是下标还是副本 id，再决定 `S0/0005` 行与 `id=16` 回包的形式。
