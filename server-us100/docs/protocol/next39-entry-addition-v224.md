# US100 进城包结构恢复：mode 分派与属性包（2026-09-18）

## 2026-11-23 已验证的 HP/MP 布局

2.24.0.124 的 USERINFO mode 1 在 23 字节前缀与角色 wire ID 后，先读取 8 字节经验，再读取 4 字节记录长度。以整份单角色 payload 起点计，长度位于 0x26，基础属性记录从 0x2a 开始，固定为 89 字节。记录开头两个 u32 分别为角色 HP 和 MP 上限的十倍，0x54 为基础百分比，0x55 为结尾 float32。空集合尾部共 43 字节，技能树数量和条目按角色存档编码。

本次角色 us100a（库内 ID 39、wire ID 1）上限为 180/140。原会话发送 34 字节占位条目时两个球显示 NaN。使用真实角色生成的 216 字节条目在城镇会话更新后，两个球都显示 100%。随后从已部署二进制启动独立服务，用数据库副本重走选角进城，新进程发出的属性包与实机验收的包逐字节一致。下文为开发过程中保留的早期假设和实验记录。


现象：角色进城后 HUD 生命/魔法球显示 `-nan(ind)%`。NaN 来自客户端的
`当前值 / 上限` 计算，上限为 0 才会得到 NaN —— 说明**属性从未送达**。

## 分派器

`0x143801b80` 即 `CNRDUserInfoPacketHandler::onNotiPacket`（函数内自带该日志字符串）。
它先读 1 字节 mode，然后：

| mode | 处理 | 结构 |
|---|---|---|
| 0 | 0x3801c3a | `u16 条目数` + 每条目 `ctx u8,u8` + 行解析器 `0x143807f80` |
| 1 | 0x3802162 | `u16 条目数` + 每条目 `ctx u8,u8` + 条目解析器 `0x1438068a0` |
| 2 | 0x3801d97 | 名单（已有布局，见 roster-v224.md） |
| 3 / 0x10 | 0x38028b6 | `u16`, `u8`, `u8` |
| 4 | 0x38021cb | `u16` + 循环 `0x143807470` |
| 6 | 0x3802244 | `u16 条目数` + 每条目 `ctx u8,u8`, `u16 键`, **raw 45 字节** → 施加函数 `0x143f0c2f0` |

mode 0 的条目解析器 `0x143807f80`：`raw 127` 字节块 → `u16 角色ID` → STRING 名字
（u32 长度 + 字节）…… 与我们已发送的 basic 包逐字段一致（frida 轨迹实测：
raw 块 23 字节处读到 u16 = 1，即角色 ID ✓）。

## mode 1（属性包）真实结构

条目解析器 `0x1438068a0` 起始即 `raw 23` 字节块，之后 `u16`、两个 `u32`。
用 marker 载荷 + frida 读值轨迹实测（`tools/us100_cursor.py`，值随偏移一起打印）：

```
off=28 raw = 0x1817161514131211   ← 23 字节块（条目内 0..23），携带我方 marker 0x11..0x27
off=30 u16 = 0x0001               ← 角色 ID（条目内 +23）
off=34 u32 = 0x77883231           ← 经验低 32 位（条目内 +25）
off=38 u32 = 0x33445566           ← 经验高 32 位（条目内 +29）
```

此后客户端不再读取本包字段：**2.38 的 250 字节前缀 + u32 长度 + 91 字节属性块
在这个 build 里根本不存在**（我们此前照搬 2.38 布局发送，客户端的字段全部落在
我们的零填充里，角色 ID 读成 0，属性自然没有生效）。

23 字节块与目录里每个职业的 11 个 `default_appearance_indices`（11×2 字节 + 1）长度
完全吻合，因此按"外观索引块"处理：`internal/character.EntryAdditionUS100` 现在发送
`{1, u16 1, ctx, ctx} + 23 字节外观块 + u16 角色ID + u32 经验 ×2`。

## 生命/魔法值

US100 里属性不经过 mode 1。分派器中 mode 6 是唯一"未知块 → 施加函数"的路径,其施加函数
`0x143f0c2f0` 经反汇编确认是一个**纯结构拷贝**（无字段解释）：

```
[rdx+0x00..0x0F] → [rcx+0x7f2]   (16 字节)
[rdx+0x10..0x1F] → [rcx+0x802]   (16 字节)
[rdx+0x20..0x27] → [rcx+0x812]   (8 字节)
[rdx+0x28..0x2B] → [rcx+0x81a]   (4 字节)
[rdx+0x2C]       → [rcx+0x81e]   (1 字节)
```

即 45 字节块就是目标对象 `+0x7f2` 处结构的镜像。`internal/character.EntryStatProbeUS100`
先把源属性 ×10 的 HP/MP 放进该块的前两个 u32（对应对象 `+0x7f2`/`+0x7f6`）作为第一轮探针；
若 HUD 仍为 NaN，则下一个候选是 mode 1 的 23 字节块（11×i16 + 1，也可能是压缩后的属性块）。

## 探针不得阻断进城

2026-09-18 事故：`EntryAdditionUS100` 的范围校验把目录里的外观索引（51265 这类
**无符号 16 位** id）判为越界，`continue` 直接中断了整个进城序列，现象是"无法进入城镇"。
两处已修：校验接受 -1..65535；探针类载荷出错时只记录事件并把载荷置空，绝不中断进城
（与任务/背包缺口的既有策略一致）。

## mode 1 必须在场，但内容不能乱填

2026-09-18 实测（三次进城对照）：

| 发送内容 | 结果 |
|---|---|
| 2.38 形状（角色 ID 落在 +250，客户端读到 0） | 加载正常结束、城镇可走（客户端查不到对象，条目被忽略） |
| US100 形状 + 真实角色 ID + 全零块 | **卡在 Loading**，右下角一直转，右上角 `ch00Unknown` |
| US100 形状 + 真实角色 ID + 目录外观索引块 | 同样卡在 Loading |
| **不发 mode 1** | 场景画出来了但**角色不能动**（服务端 0 条位置更新） |
| US100 形状 + **不匹配的键（0）+ 全零块**（`-entry-addition-stub`） | 加载结束、城镇可走、零错误 ✓ |

结论：客户端**必须收到 mode 1 才会离开加载状态**；而一旦条目被真正应用（键命中角色），
由于块内语义尚未恢复，加载会被卡住。所以可游玩路径暂时发送"形状正确、键不命中"的
stub（`UserInfoAdditionStubUS100`），把恢复工作留给显式开关。

## 属性通道：当前结论与边界（2026-09-18）

已排除的通道（都用"逐字节渐变"标记法测过，保证 u8/u16/u32 字段都能读到非零值）：

| 通道 | 结果 |
|---|---|
| mode-1 的 23 字节块（进城期 / 城内重发） | HP/MP 无变化；进城期一律卡加载或 20 秒后客户端退出 |
| mode-0 的 127 字节块 | 是**文本结构**（状态窗口渲染出 `0123456789:;<=>?@ABC…`），声望字段被读出（u16 左移 8 位），HP/MP 无变化 |
| mode-6 的 45 字节块（对象 `+0x7f2` 纯结构拷贝） | 无可见变化 |

另外测出：**mode-1 条目的经验字段之后还有被消费的字段**——把 23 字节块填成"空外观"
（所有槽位 `0xffff`，对无装备角色语义正确）时，客户端会继续往后读；只填 0 或目录外观
列表时它会停在经验处。这些后续字段由**场景初始化代码**（调用点 `0x4e6edf3` 等）读取，
与进城状态机耦合：填任何不完整内容都会让客户端卡在 Loading（补 512 字节渐变尾巴也一样，
客户端并不读尾巴，说明不是长度问题而是内容问题）。

因此当前策略：可游玩路径发送**形状正确但键不匹配任何角色**的 stub
（`UserInfoAdditionStubUS100`），客户端据此离开加载状态且不应用任何未恢复字段；
城镇完全可交互（实测有位置更新）。HP/MP 仍是 `-nan(ind)%`，属性通道留待一次
"从客户端属性结算代码反推"的深度恢复（找 2.38 `145cce150` 对应函数 → 其调用者 →
下发属性的包），不再用反复进出城试错。

## 23 字节块的字段表（2026-09-21 静态取证，权威）

方法：把块所在的全局（`0x149477580`）当作地址范围，用 `tools/xref_range.py` 扫全 `.text`
的 RIP 相对引用（分块 + 16 字节重叠，避免跨块误码）。**全部 15 处引用都在同一个函数里**
（mode-1 条目解析器 `0x1438068a0`），因此这张表来自**客户端自己的读取**，不是猜的：

```
block+0   u32   (0x3807002 mov edi, dword [block+0])
block+4   u64   (0x3807008 mov rsi, qword [block+4])
block+12  u8    (0x380705c cmp byte [block+12], 0 -> setg -> 0x143f0b990)
block+13  u8    (0x3806b19 cmp byte [block+13], 0 -> setg -> 0x143f0b930)
block+14  u8    (0x380706e cmp byte [block+14], 0 -> setg -> 0x143f0b8d0)
block+15  u8    (0x3807317 movzx edx -> 0x143d4ae00(rbx, value))
block+16  u8    (0x3807326 movzx edx -> 0x143d4ae10(rbx, value))
block+17  i8    (0x3807375 movsx edi -> 0x143eeff90 / 0x143d4ae20)   ← 有符号
block+18  i8    (0x3807381 movsx edi -> 同上，循环第 2 次用)          ← 有符号
block+19  u32   (0x38073b3 mov edx -> 0x143f0b9f0(actor, value))
```

`4+8+1+1+1+1+1+1+1+4 = 23`，**正好填满，无空档**。旧文档里"11×u16 外观索引 + 1 字节"的
假设**由此推翻**：块是一组混合字段，不是索引表。

用法（同一函数内的应用点，`r13` = 按 key 查到的 actor 对象）：

| 字段 | 应用 |
|---|---|
| +0 (u32) | `mov [actor+0x434], edi`，并把该值传给 `0x142b58dc0(actor, value)` |
| +4 (u64) | `mov [actor+0x438], rsi`，并把该值传给 `0x142b58e30(actor, value)` |
| +12/+13/+14 | 各是一个布尔（`值 > 0`），分别经 `0x143f0b990/930/8d0` **置位对象 `+0x1d8` 的标志字**（+13 那条确认是 `shl 4` → bit 0x10，再 `or` 回 `[rax+0x1d8]`） |
| +15 / +16 | 两个 u8，分别喂 `0x143d4ae00` / `0x143d4ae10` 两个相邻 setter |
| +17 / +18 | 一对**有符号字节**，在一个跑两次的循环里依次使用（第 1 次 +17、第 2 次 +18），喂 `0x143eeff90(obj, v)` 与 `0x143d4ae20(rbx, index, v)` |
| +19 (u32) | 喂 `0x143f0b9f0(actor, value)`（与上面三个置位函数相邻的另一个 setter） |

块之后**包体还有被读取的字段**（解析器继续读 `u8@25, u8@26, u32@27, u32@31, u8@35,
u8@36, u16@37, u8@39`；本文件早前那轮 marker 轨迹只到经验就停，是载荷形状没触发后续读取）。
`UserInfoAdditionUS100` 目前只发"块 + u16 键 + 两个 u32"，与这条读链并不对齐——这是下一步要改的。

另外解析器里有一条失败分支会打印 `'FATAL ERROR : ... serverId(%d) ...'`（`0x1438073c3`）：
key 查不到角色时就走那里。我们的可玩路径正是靠"键不命中"来跳过应用，所以这条日志
在可玩局里**必然出现**，看到它不等于出错。

## 属性结算链（2026-09-21 静态取证，新）

从 mode-1 条目解析器（`0x1438068a0`）反查调用点，取出它调用过的函数并逐个反汇编，
得到一条以前没有记录的链：

```
mode-1 解析器 ─► 0x143f03330(actor rcx, flag dl = 23 字节块的字节13 > 0)
                 ├─ lea rbp, [rcx+0x678]                 ← actor 内的子对象
                 ├─ mov ecx, 0x23a8 ; call 0x144f29780    ← 申请 9128 字节"属性对象"
                 ├─ call 0x143be60f0                      ← 构造
                 ├─ call 0x143f0c440(actor, 属性对象)
                 ├─ 虚调用 [rax+0x8e0](actor+0xd8, 0, 0, flag, 0)
                 ├─ movzx ebx, word [actor+0xc8]
                 ├─ call 0x143c21080 / 0x143c16c80 (属性对象, actor)
                 ├─ call 0x143c21110(属性对象, actor+0x7f2)  ← ★ 45 字节属性结构被吃进去
                 └─ call 0x144b1e4f0(actor, 属性对象, [actor+0xb50], 1)
                        （内部是引用计数对象的遍历：0x143c095a0/0x143c1c620/0x143c1c5b0…）
```

关键点：**结算函数消费 `actor+0x7f2`，而 mode 6 正是往 `actor+0x7f2` 拷贝那 45 字节**。
所以客户端期望的顺序是 **mode 6 先填 → mode 1（键命中）触发结算**。

对照历史实验：mode 6 单独发过（无可见变化）、mode 1 用**不命中**的键发过（等于根本不触发
结算）。**"mode 6 先 + mode 1 命中"这个组合从未试过。**

`entry_flow.go` 的顺序原先也是反的（mode 1 在前），2026-09-21 已改为 mode 6 在前，
并在 `packets()` 上写明依据。

## 探针必须用 frida spawn，不能用 attach（2026-09-21 实测）

同一份处理器探针，`device.spawn` + 早期挂载 **对照组命中**（`handler 36/37` 在进城时触发）；
而 attach 到已经跑起来的客户端时 **零命中**（两次，含必然被处理的对照 id）。
结论：这个客户端（Themida 壳）会把事后写入的 trampoline 还原掉，**所有客户端探针都要走
spawn**。这条同时解释了本文早前"处理器入口探针零命中、包在派发前被丢弃"的旧结论——
那次很可能是探针没生效，而不是包被丢。

## +0 / +4 两个消费者是纯赋值（2026-09-21 静态取证，新）

上一节说 +0/+4 分别"传给 `0x142b58dc0` / `0x142b58e30`"，语义未定。这次把两个函数
本身反汇编出来（`tools/dis_range.py <addr> [len]`），结论是**它们不做任何解释**：

```
142b58dc0  test rdx, rdx / je ...        ; rcx=actor 收件人, rdx=目标对象, r8d=值
           call 0x140467c90              ; = lea rax,[rcx+0xd8]; ret  ← 只是取 actor+0xd8
           mov [rax+0x434], edi          ; *(u32*)((actor+0xd8)+0x434) = 值
           mov rcx,[0x149788d80]         ; 单例（0x142b58b00 取的同一个）
           cmp rax, rbx / jne
           mov [rsi+0x4c], edi           ; 单例+0x4c = 值（同一个值的镜像）
142b58e30  同形，但是 64 位：mov [rax+0x438], rdi / mov [rsi+0x50], rdi
```

两点影响：

1. **没有查表、没有索引**，所以往 +0/+4 放较大数值本身不会越界。此前"标记字节导致
   解析器崩"不能归因于 +0/+4，只可能来自别的字段（例如 +15..+19 或尾部字段错位）。
2. 落点其实是 **actor+0x50c（u32）与 actor+0x510（u64）**（因为取对象就是 `actor+0xd8`），
   而不是字面上的 +0x434/+0x438。用 0x50c 做偏移引用扫描命中太杂（那是一片通用容器
   对象的公共偏移），**名字仍只能由 HUD 实测定**。

所以 +0/+4 的取值仍按 90/115 两个参考服务端的战斗 blob 头部处理：+0 = 最大 HP，
+4 = 最大 MP（×10）。**这条只是"最可信的候选"，不是已证实的语义**。

## 一次运行同时判定"哪个通道"（2026-09-21，attr-pair）

历史实验从没跑过的组合是 **mode 6 先填 + mode 1 键命中触发结算**（见上节）。现在
`tools/us100_interactive.py` 的 `attr-pair` 风格就是它，且两条通道刻意用**不同数量级**
的哨兵值，这样一次加载就能同时回答两个问题：

| 通道 | 载荷 | HUD 若显示 |
|---|---|---|
| mode 6（45 字节，两对槽位都填） | HP 对 = 777/777，MP 对 = 888/888 | 777/888 或 77/88 → **mode 6 是 HUD 来源** |
| mode 1（23 字节块 +0/+4） | +0 = hp_max×10 = 1800，+4 = mp_max×10 = 1400 | 1800/1400 或 180/140 → **mode 1 是 HUD 来源** |

两个哨兵值互不混淆，且都远离 0，所以"仍是 -nan(ind)%"这个结果本身也有意义：
它说明上限仍然来自别处（既不是这两条通道，也不是它们的组合）。
`entry_addition_mode` 事件会记录 `stat_hp`/`stat_mp`/`addition_bytes`/`stat_bytes`，
事后可核对这一局究竟发了什么。

## 面板读数来源与 CN90 参考（2026-09-21 晚，新证据）

### 已定：面板读的是 actor，不是线上镜像结构

- `0x149477500` 是 **127 字节 userinfo 镜像**：清零函数 `0x1438045d0` 正好写
  `7×movups + qword + dword + word + byte = 112+8+4+2+1 = 127`，块的边界由此确认。
- 对该结构与相邻区（`0x149477500..0x149477600`）的 **全部 281 处代码引用**只落在
  解析器/清空/标志检查里（`0x143807f80` mode-0、`0x1438068a0` mode-1、`0x14380a470`
  mode-3、`0x143803320`、`0x1438045d0`、`0x143805230`、`0x143805635`、`0x143854d80`、
  `0x1438550e0`、`0x143855240`、`0x1426abf60`、`0x1433b09e0`、`0x14376d480`、
  `0x1400258f0`）——**没有一处是 UI**。
- 实测（本会话）：注入 mode-1（键命中）后，镜像里仍是旧的 ramp 块，但面板
  "Adventurer Fame" 立刻从 `1,056,256` 变成 `0` → **面板读的是 actor 上的值，且
  mode-1 的应用路径会在角色上重算属性**（fame 被重算成 0，因为角色没有装备/基础数据）。
- 推论：mode-0 的块只把值写进 actor（如 fame），**改线上镜像不会改面板**；要动面板
  只能改包（写 actor）或直接写 actor 的字段。

## 属性记录放在 body 0x1f 会把解析器读链撞乱（2026-09-22 实测，重要）

**现象**：用 `style=stats`（mode-1 body 0x1b=92、0x1f=92 字节记录）进城，客户端在进城后
**约 0.5 秒**以 `0xC0000005` 退出；退出前服务端事件正常（`completed_quests_restored`、
`client_frame 318/31/143/433/140/707`），随后 `close`。同一套服务端换回 `attr-pair`
（hp 块 + mode-6 marker，body 0x1b/0x1f 全零）即可正常进城——即崩溃由**记录本身**引起，
不是启动器/环境。

**原因（有字节为证）**：把当次发出的载荷解出来：

```
body 0x1b u32 = 92          （记录长度）
body 0x1f u32 = 1800        （hp_max×10）
body 0x23     = 120         ← 记录第 4 字节 = mp_max 的低字节（1400 = 0x578）
body 0x27 4×u16 = 75,75,45,45（四维 = 物攻/物防/魔攻/魔防 ×10）
body 0x73     = 100         （基础属性百分比）
```

而 mode-1 解析器在 **0x23 读一个计数**，然后按"每项 u16+u8"的循环消费
（反汇编 `0x143806be0` 读计数、`0x143806c30..0x143806d0f` 循环；`count` 存
`[rsp+0x42]`）。记录放在 0x1f 时，这个计数被记录内容写成了 **120**，循环要读
120×3 = 360 字节，而载荷只有 256 字节 → 越界读 + 状态被写乱 → 进城即崩。

**结论**：CN90 的"body 0x1f 放整块属性记录"**不能直接搬到这个 build**；US100 的 mode-1
在 key 之后是一串**结构化字段**（计数 + 列表 + 若干标量），不是单一 blob。之前能进城的
所有载荷都是在这些位置写 0（计数 0 → 循环不执行）才安全的。

**因此**：
- `tools/us100_interactive.py` 的 `stats` 风格已改注释，明确标注为**探针、会崩**；
  可玩的默认仍是 `attr-pair`（或更朴素的历史风格）。
- `-entry-addition-stats` / `protocol.EntryStatBlobUS100` 的实现保留（字段顺序、长度位、
  百分比位都对），但**在定位真正的消费点之前不要用可玩路径发它**。
- 下一步必须换工具：用 **spawn** 方式（attach 无效，见前文）在 mode-1 解析器
  `0x1438068a0`（以及 mode-3 的 `0x14380a470`）上打**读取探针**，直接看：
  ① 每个读取位于 payload 的哪个偏移；② 值最终落到哪里（actor 偏移 / setter 调用）。
  四维与 HP/MP 的真正入口就在这些存储点里，而不是在"已知的对齐"里。

**四维数据源已确认（顺带）**：本代客户端的能力字符串表把 PHYSICAL_ATTACK /
PHYSICAL_DEFENSE / MAGICAL_ATTACK / MAGICAL_DEFENSE 显示为 力量/体力/智力/精神
（CN90 `charstat/load.go` 的注释，他们也是这么补的）。我们的 .chr 正好只有这四项，
所以四维按物攻/物防/魔攻/魔防×10 填（`character.EntryAdditionStatsUS100` 已实现）。

## HP 通道已打通：CMD 1959（2026-09-22，活体验证）

### 结论（全部经活体验证，可复现）

**HUD/面板的当前 HP 不走任何 USERINFO 记录，而走一条专用命令：**

```
kind 1 (CMD)  id 1959 (0x7a7)   body = [u8 1][u32 当前HP]   单位 = 显示值 ×10
```

- 处理器 `0x14348ef90`：`test dl,dl` 后从包游标读 u8(1)、再读 u32，写入全局加密字段
  `0x149787ce0`（当前 HP）与 `0x149787cf0`（tick 时间戳），并顺带刷新
  `0x149787ce8`（MP，值取自 getter `0x146082b14`）。
- 加密：`decode(x) = (x ^ 0x1f2a025c) - 4`，写入 `[f]=(v+4)^0x1f2a025c`、
  `[f+4] = v + [f] + 0xc4`；校验失败时由 `0x147b96708` 修回。
- HUD getter `0x143a76820`：`当前HP = decode(ce0) + (tick - decode(cf0)) × rate`，
  rate = [0x1464bfc24] = 0.001（每 tick 回 0.001，基本可忽略）。
- 实测三次写入：4 字节 body（缺前导 u8）→ 字段得 7（= 0x0708>>8，游标错位读
  body[1..4]）；5 字节 `[1][1800]` → 字段解出 **1800**，guard `[ce4]` 逐位吻合。

### 事实（全部实测，非推测）
1. 入场 stat 对象（ctor 0x143be60f0，9128 字节）的槽区只写默认值：
   +0x1108=40、+0x1144=100、+0x1110/+0x114c=-1、+0x21fc=100、+0x2204=-1、
   +0x11ec=1.0f（caller 0x143c21040 每帧刷新）、+0x2224/+0x222c=升级经验曲线迭代（4663,4781,...×1033 级）。
   **没有任何 HP/MP/四维真值写入 → 115 式"记录→40槽展开"函数在 US100 入场路径不存在。**
2. 按 A 打开面板后出现 11 个新解码调用方（面板读取端）：
   0x143c00f85、0x143c0141e、0x143c01469、0x143c01789、0x143c018bd、0x143c0200d、
   0x143c02540、0x143c027fb、0x143c02863、0x143f06123、0x143f06173。
   读取对象不是 stat 对象，而是另一堆对象（样本槽指针 8 字节步长：+0x30c/+0x314/+0x31c/+0x334，
   对象基址=槽指针-0x30c）。读取模式=decode+guard 校验+失配调修复 0x147b96708。
3. 面板槽写方=0x142eb48d0/0x142ebaf70：对每个槽调用带索引 stat getter
   （0x143edf9e0 float / 0x143ed8e50 int / 0x143edafc0 float，索引 edx=0,1,2,0xcd...），
   stat 源 r14 经虚调用 [vtable+0x1db0](obj+0xe0 上下文, type=0x44, 1) 获得；
   结果 cvttss2si 后 encode 写入 obj+0x304..+0x334（值槽+guard 槽成对）。
4. 另发现 0x143805312（USERINFO 分发器领地）直接写 +0x32c —— 包驱动的面板槽写入点。

### 结论
US100 面板 = 计算型管线：mode-1/mode-6 → actor 字段 → stat 计算管线 → 索引 getter →
面板写方 0x142eb48d0 → 槽 +0x304.. → 面板 getter → UI。
点亮面板的正确路径不是找"展开函数"，而是**补齐 stat 计算管线的输入**：
mode-1 尾部结构字段（u8@25,26、u32@27,31、counted (u16,u8) 列表、STRING@71...）。
